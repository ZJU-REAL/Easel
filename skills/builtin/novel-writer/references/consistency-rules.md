# 一致性规则（长篇不崩的机制）

> 长篇网文最大的技术难点：写到第 80 章时，人设/世界观/时间线/伏笔与前文冲突。
> 解法 = **文件即真相 + 按需加载 + 定稿即更新 + 写前扫冲突**（三家开源共识）。
> 本文件规定 `bible/` 与 `state/` 的更新纪律。

## 一、职责划分：bible（不变的） vs state（在变的）

- **bible/**（硬约束，很少变）：
  - `world.md` 世界观规则、力量体系、地理——一旦定下，正文不得违背。
  - `characters.md` 角色的固定属性（身份/外貌/性格底色/关系初始态）。
  - `voice.md` 文风指纹 + 禁用词。
  - `canon.md` 已发生的**硬事实**：时间线、关键事件、伏笔登记（埋下→回收）。**这是跨章一致性的总账本。**
- **state/**（随剧情推进，每章更新）：
  - `summary.md` 滚动前情提要（text-condenser 压缩生成）。
  - `character-state.md` 角色**当前**位置/处境/关系/持有物/已知信息。
  - `plot-arcs.md` 各条明线/暗线的当前进度。
  - `progress.json`/`.md` 章节进度（novel_ops.py record 维护）。

> 判断某信息该放哪：**会不会随剧情改变**？不会→bible；会→state。

## 二、写每章「按需加载」清单（不塞全书）

写第 N 章只读：
1. **全部 `bible/`**（硬约束，必读，通常不长）。
2. `outline/chapters.md` 里**第 N 章那一行**（+ 需要时看本卷 arc）。
3. `state/summary.md`（前情提要，代替读前面所有正文）。
4. `state/character-state.md` 里**本章在场角色**的当前状态。
5. 若本章回收伏笔：`bible/canon.md` 里该伏笔的埋点。

**不要**把 chapters/ 里的历史正文全读进来——那正是长上下文漂移的根源，summary.md 就是为此存在。

## 三、定稿即更新（sync，每章写完必做）

顺序：
1. **canon.md**：登记本章新发生的硬事实（新事件/新设定/时间推进）；更新伏笔状态（新埋的登记，回收的标记已回收）。
2. **character-state.md**：更新本章中状态有变的角色（位置/关系/新获得/新伤病/新信息）。
3. **plot-arcs.md**：推进相关情节线。
4. **summary.md**：用 text-condenser 把「截至本章的剧情」重新压缩（滚动更新，控制长度，保留主线与未回收伏笔）。
5. **progress**：`novel_ops.py record ... --status done --when <日期>`。

## 四、写前/写后冲突扫描

- **写前**：对照 bible/canon 确认本章计划不违背既定事实（角色不会出现在两地、死人不复活、能力不超设定）。
- **写后**：机械跑 `novel_ops.py slopcheck`（AI 味）；人工对照 canon 复查时间线与人设。
- **发现冲突**：优先改正文使其符合 canon；确需改设定则**向下级联**（autonovel 的 propagation debt）——改了 bible 就要检查受影响的大纲与后续章是否需要连带修订，别只改一处留下矛盾。

## 五、修订闭环（可选，提升连贯性）

长篇初稿连贯性常不足。可在若干章后做一轮 revise：
- 补过渡（突兀的场景切换加衔接）。
- 统一称呼/时间戳/地名（易漂移处）。
- 替换重复措辞（slopcheck 高频词）。
- 检查伏笔是否都在计划回收——canon 里长期「埋下」未回收的要么回收要么删。

> 经验（xindoo/ai-novel-lab）：一轮系统修订能把连贯性评分从「及格」拉到「优秀」。别跳过。
